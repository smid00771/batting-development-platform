# Selection call access revocation

This internal worker ejects and bans revoked Selection Room entry identities from their existing Daily room. The database decides which entries lost access after group grants, heads or membership change. Other groups and still-authorised selectors remain in the call. The worker does not settle, release or alter call credit reservations; the existing verified-usage worker retains that responsibility.

The request accepts only a random one-time `{run_id, token}` capability. The service-role-only `selection_video_revocation_worker` RPC authenticates it and leases at most five room jobs, each containing up to 100 entry UUIDs. The worker validates the full batch and the exact room name derived from the call UUID before contacting Daily. It sends `{user_ids: entry_ids, ban: true}` to the fixed Daily room-ejection endpoint. Caller-supplied rooms, users and provider URLs are rejected.

A successful response must contain an `ejectedIds` array before the exact leased entries are marked complete. Every provider error, including HTTP 404, malformed response and timeout, defers the work. A failed completion is safe to retry: the same entry identities are banned again. If deferral itself fails, the database lease expires for retry. Error responses contain no provider bodies, credentials or capabilities. Five room jobs run concurrently with eight-second deadlines per network operation, bounding network waits to 32 seconds even when completion and deferral both fail.

## Deployment and verification

Deploy as `selection-video-revoke` with gateway JWT verification **disabled**; its one-time capability supplies custom authentication. Keep JWT verification enabled for the separate user-facing `selection-video` function. Required server environment variables are `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` and `DAILY_API_KEY`. Never expose them to browsers. The accompanying database migration installs the capability RPC, queue and scheduler; deployment and scheduler activation require the release workflow. The migration leaves both the cron job and `selection_video_revocation_settings.enabled` off. After deploying this worker, verify that a one-use capability reaches the service RPC, then enable that private setting and the `selection-video-revocations` cron job in one transaction. Until enabled, new scoped calls and permission changes that would invalidate active tokens fail closed. Deploy the updated user-facing `selection-video` function with its post-token admission check as part of the same beta release.

Run `node --test Tests/selection_video_revoke_test.mjs`. These tests use mock provider and database responses and make no live API calls.

As rollout verification, and before wider public launch, exercise a real disposable Daily room: revoke an active participant and confirm ejection, attempt rejoin with the original token, repeat while that participant is disconnected, and confirm that still-authorised participants remain connected. The [Daily eject API](https://docs.daily.co/reference/rest-api/rooms/session/eject) documents that `ban: true` prevents the supplied `user_ids` from rejoining. It returns ejected participant IDs rather than a persisted-ban acknowledgement. This worker accepts an empty `ejectedIds` list because an identity can be disconnected; the documentation does not explicitly establish disconnected-user ban persistence or its lifetime across meeting sessions. Mock tests cannot establish those provider behaviours. The implementation relies on Daily’s documented rejoin-prevention contract. If rollout verification contradicts that contract, keep scoped calls disabled until an alternative is verified. Local tests alone are not evidence of end-to-end provider enforcement.

Revocation is asynchronous. Database admission denies new tokens immediately, and the queue requests provider enforcement after commit with scheduled retries. A provider outage or dispatch delay can leave an existing token usable until a successful ban or its existing expiry. Do not promise instant ejection or claim live-provider verification from the local tests.

A permission transaction queues a post-commit dispatch immediately. Failed provider work is eligible after 20 seconds and the cron runs every minute; an interrupted worker lease expires after two minutes. Queue backlog or provider/database outages can extend enforcement delay, bounded ultimately by the existing token expiry (at most 90 minutes). Revocation does not promise synchronous ejection.
